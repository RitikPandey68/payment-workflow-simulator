Exponential Backoff Retry Engine

          
When a webhook delivery fails, the system queues it for automatic retry using exponential backoff with jitter — preventing the thundering herd problem.


          

            

              

              

                Attempt 1
                Immediate delivery
              

            

            

            

              

              

                Attempt 2
                ~1 second delay
              

            

            

            

              

              

                Attempt 3
                ~2 second delay
              

            

            

            

              

              

                Attempt 4
                ~4 second delay
              

            

            

            

              

              

                Attempt 5
                ~8 second delay → EXHAUSTED
              

            

          


          

            
Delay Formula

            
delay = base_delay × 2(attempt-1) ± 20% jitter

Idempotency Failures

              HIGH RISK
            

          

          
Without idempotency, retrying a failed network request can result in double charges. The simulator enforces idempotency keys to prevent this.

          

            

              
1. Client sends POST /orders with Idempotency-Key: abc123

              
2. Network times out — client retries with same key

              
3. Server replays cached response — no duplicate order ✓

            

          

          
        


        

          

            🔐
            

              
HMAC Signature Mismatch

              CRITICAL
            

          

          
If merchants don't verify webhook signatures, attackers can forge fake payment events. Always validate the X-Razorpay-Signature header.

          

            

              
1. Attacker sends fake payment.captured event

              
2. HMAC signature doesn't match webhook secret

              
3. Event REJECTED — merchant protected ✓

            

          

          
        


        

          

            📬
            

              
Duplicate Webhook Events

              HIGH RISK
            

          

          
Payment gateways may deliver the same event multiple times during retries. Merchants must implement idempotent webhook handlers using event IDs.

          

            

              
1. Gateway delivers payment.captured (evt_001)

              
2. Retry fires same event again (evt_001)

              
3. Simulator detects duplicate by event_id ✓

            

          

          
        


        

          

            🔄
            

              
Retry Exhaustion

              MEDIUM
            

          

          
If a merchant endpoint is consistently down, webhooks will be retried up to 5 times then marked EXHAUSTED. The merchant must reconcile missed events manually.

          

            

              
1. Webhook delivered → 500 error

              
2. Retry 1-4 → all fail

              
3. Retry 5 → EXHAUSTED, no more retries
